# Compatibility notes

- The original paper-era requirements target Python 3.10.13, PyTorch 2.0.1, torchvision 0.15.2, and PyTorch Geometric 2.3.1; original pins are recorded in `requirements.txt` and the paper-era repository.
- This host is Apple Silicon macOS (arm64) with an Apple M3 and 16 GB unified memory. CUDA is unavailable. The installed system PyTorch 2.10.0 reports both CUDA and MPS unavailable. No system packages were modified.
- Paper-era `happy.utils.utils.get_device()` chooses only CUDA or CPU; it does not select Apple's MPS backend. The supplied scripts therefore use CPU on this Mac even if the isolated PyTorch wheel were to expose MPS.
- The paper reports training on a single NVIDIA A100. This host cannot provide that accelerator. Full RetinaNet, ResNet-50 and especially 2,000-epoch 16-layer ClusterGCN training on CPU is not currently a realistic substitute for the reported hardware schedule. Any CPU result must be labeled with its hardware and runtime.
- WSI reading may require native libvips/OpenSlide and Java/Bio-Formats components. The released training tiles and embeddings avoid these native reader dependencies for the three core training/evaluation stages.
- Do not load Zenodo `trained_models` as reproduction checkpoints. They may be used only for an explicitly labelled inference/debug comparison. COCO/ImageNet weights are permissible initialisations because the paper specifies them for the first two stages; the graph model must start randomly initialised.
- Paper prose says the RetinaNet stage was fine-tuned from COCO, but paper-era v1.0.0 code loads only torchvision's ImageNet ResNet-101 backbone weights and initialises the detector feature pyramid/heads. The runner follows code behavior. This prevents asserting exact initialization fidelity.
- Historical PyTorch and PyG binary compatibility on macOS arm64 must be established in the isolated environment before execution. If incompatible, record the exact resolver/import error and create a documented minimal compatibility environment; do not silently upgrade architecture or major dependencies.
- The official PyG wheel index for the paper-era PyTorch 2.0 CPU stack lists macOS x86_64 wheels for optional graph extensions but no matching arm64 wheels. The core `torch-geometric` package can install, but `ClusterData`/`NeighborSampler` depend on optional compiled components; graph-stage execution on this Apple Silicon host may require a source build or a Linux x86_64/A100 environment. Any substitute stack must be reported as modified.
- Core isolated package installation completed: PyTorch 2.0.1, torchvision 0.15.2, PyG 2.3.1, and editable HAPPY imports for nuclei/cell succeeded. Runtime reports CUDA=False and MPS=False. A graph import smoke then failed with `ModuleNotFoundError: No module named 'torch_cluster'`.
- The paper-era README/Makefile CPU extension command was attempted and failed immediately: `No matching distribution found for pyg_lib` on arm64. A source build attempt for `torch-cluster==1.6.1` and `torch-sparse==0.6.17` also failed, as described below.
- The source build attempt failed in `torch_sparse` while compiling against this host's Xcode libc++: `is_arithmetic cannot be specialized: Users are not allowed to specialize this standard library entity`. Pip did not install the graph extensions. The default all-stage runner now checks these imports before starting nuclei/cell training to avoid spending CPU time on stages when the requested three-stage run cannot finish.
- The first full `pip install -r environment/requirements.txt` attempt failed while building `python-javabridge==4.0.3`, required by `python-bioformats==4.0.7`. The actual setup error was `Could not find Java JRE compatible with x86_64 architecture` / `Exception: JVM not found`. These three WSI reader packages have been isolated in `requirements-wsi.txt`; the core paper training inputs are already tiles and HDF5 embeddings, so they are not imported by the core model scripts. Raw-slide processing remains unavailable until a compatible ARM64 JDK/JVM and native slide-reader libraries are installed and verified.
- The original graph trainer logs training loss and validation accuracy, but not validation loss. The plotting utility will create the training-loss curve available in the original stats; it will not invent a graph validation-loss series.
- A fresh diagnostic confirms the isolated environment is Python 3.10.0 on macOS arm64 with torch 2.0.1, torchvision 0.15.2, PyG 2.3.1, and no CUDA or MPS. Imports for `torch_cluster`, `torch_sparse`, `torch_scatter`, and `pyg_lib` all fail because no binary operators are installed.
- The PyG official [2.0.0 CPU wheel index](https://data.pyg.org/whl/torch-2.0.0%2Bcpu.html) has Python 3.10 Linux x86_64 wheels for the pinned extension versions and macOS x86_64 wheels, but no macOS arm64 wheel. The paper-era extension install was attempted on this Mac and the source build failure is recorded above. The current PyG installation guide now describes newer packages/APIs; do not apply its latest package versions to the paper-era PyG 2.3.1 code.
- Linux/GPU execution was investigated locally: `nvidia-smi` is absent; Docker CLI exists, but the Docker daemon is not running; no configured Linux GPU runner is available in this workspace. The README contains a pinned Linux x86_64/CUDA 11.8 setup command and an operator smoke check. That environment remains unverified until run on an actual Linux host with a compatible GPU.
- Before Zenodo archive 001 completed, the requested reproduction smoke command `.venv/bin/python scripts/run_public_reproduction.py --stage nuclei --smoke-test` correctly exited with `Prepared data missing`. After the verified archives were prepared, the next attempt passed CLI parsing and reached the required ImageNet weight download. Graph-stage smoke remains blocked by absent operators.
- After the verified archives were prepared, the first nuclei smoke exposed Typer 0.9.0 incompatibility with the transitively installed Click 8.5.0 (`Secondary flag is not valid for non-boolean flag`). Pinning `click==8.1.7` fixed CLI parsing. The next smoke reached the original ImageNet ResNet-101 weight fetch; network access from Python was blocked in the sandbox, so `scripts/download_pretrained_weights.sh` now fetches the paper-specified official initializers via curl and checks their SHA256 filename prefixes before training.
- Upstream v1.0.0 training scripts save model state dictionaries or graph model objects but do not save optimizer, scheduler, or RNG state. Exact interruption resume is not supported by the upstream code. The reproduction runner refuses to silently restart an existing run directory; resuming only from weights would change the optimizer trajectory and must be labeled a modified run.
- To avoid the restricted macOS shared-memory failure, the reproduction runner sets data-loader `num_workers=0` on Darwin only; the paper's Linux/A100 path retains each upstream default. This does not change batch size, learning rate, model, split, or epoch schedule.
- Nuclei smoke execution: one initialization-phase epoch completed on the 178-image training split and saved `nuclei_final_model.pt` plus training statistics. Validation F1 was 0 for this deliberately tiny smoke run. A second one-epoch fine-tuning smoke started at LR 0.001 from the one-epoch warm-up and immediately produced infinite loss, so it was stopped and excluded. The smoke runner now checks only the initialization phase; full runs still use the specified 40+60 epochs.
- Cell smoke execution: one complete initialization-phase epoch ran on the released 13,480-image train split with finite loss; log shows train accuracy 0.1916 and validation accuracy 0.2876 (smoke-only, not a paper test result). The original trainer saved its best smoke checkpoint `cell_model_accuracy_0.2876.pt`, then the child process exited with SIGABRT during post-validation confusion-matrix plotting before writing final stats/hyperparameters. The checkpoint is retained and was not used for any report metric.
- The graph trainer calls the source `set_seed` with its CLI default of 0. The nuclei and cell training entry points expose no seed parameter and do not set a fixed seed; record those stages as seed-unspecified rather than introducing a new seed and implying it matches the paper. Runtime and command lines are logged by the reproduction runner; package pins are in `environment/requirements.txt`/`pip_freeze.txt`, and host details are in `environment/system_info.txt`.

## Local M3 cell plotting fix and execution (2026-10-15)

- The macOS diagnostic for the earlier SIGABRT shows Matplotlib entering the AppKit `NSApplication` initialization path. Local runner-launched child processes now default to `MPLBACKEND=Agg`; cell training also treats Python plotting exceptions as nonfatal. Model, initialization, augmentation, split, optimizer, scheduler, epoch, batch, and metric code were not changed.
- Paper-era cell and nuclei evaluators save numerical JSON before optional plots. Cell evaluation saves `y_true`, `y_pred`, and model logits to NPZ files. Nuclei evaluation saves per-image GT/predicted point records and metric JSON. Evaluator DataLoaders use zero workers on Darwin, matching the already-used training workaround; the original three-worker evaluator failed locally with `torch_shm_manager: Operation not permitted`.
- A new cell smoke run completed its one ImageNet-initialized frozen epoch on CPU in 1,694.55 seconds. It wrote `cell_train_stats.csv`, `cell_final_model.pt`, the best-validation checkpoint and all four validation confusion matrices under `projects/placenta/results/cell_class/repro-cell-plotfix-smoke/`. The diagnostic validation accuracy was 0.209; it is smoke-only and excluded from comparison reports.
- The evaluator was run against this smoke checkpoint on validation splits solely to verify persistence: it wrote four prediction NPZs (including an 11-logit column per cell) and metric JSON before plots under `projects/placenta/results/reproduction_evaluation/cell_class/validation/`. These are smoke-checkpoint validation outputs, not test or paper reproduction metrics. Class IDs 0–10 map to CYT, FIB, HOF, SYN, VEN, MAT, VMY, WBC, MES, EVT, KNT in `happy/organs.py`.
- Direct evidence: `logs/repro-cell-plotfix-smoke.log` and `logs/repro-cell-validation-output-smoke.log`. Full schedules were not launched. One cell epoch projects to about 75.3 hours for 160 epochs, before phase-two slowdown/variation. The host had 8.6 GiB free afterward; saved checkpoints are retained rather than pruned, so available space is also inadequate for a long run that creates multiple best-checkpoint files. The existing nuclei smoke checkpoint is retained; no nuclei test evaluation or full schedule ran.
- The verified public test annotation files remain present: nuclei test CSV line counts are 890 HMC + 1,864 UOT rows (2,754 nuclei) plus 11 empty-image annotation rows; cell test CSVs contain 686 HMC + 1,695 UOT + 362 NUH rows (2,743 cells). These test labels were not evaluated because no full model was trained.
